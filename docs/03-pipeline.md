# 03. Пайплайн анализа

Образец — `pipeline.ts` из worklog-tracker: `runAnalysis()` в `src/lib/pipeline.ts` только оркестрирует стадии, общий `RunContext` передаётся каждой. Стадия Scan вызывает Rust (`api.scanRepo`), остальные стадии — TypeScript.

## Стадии

| # | Стадия | Что делает | LLM | Где |
|---|---|---|---|---|
| 1 | **Scan** | `Extractor` и `ContextSource` собирают точки входа, компоненты, вызовы, обращения к хранилищам и внешним системам | нет | Rust |
| 2 | **Discover** | группирует точки входа в кандидатов-фичи (по путям, классам, тегам OpenAPI) | опционально: именование | TS |
| 3 | **Trace** | для каждой фичи строит граф от триггера до стоков; помечает обрывы (DI, рефлексия, события) | нет | TS |
| 4 | **Describe** | бизнес-названия, краткие описания | да (через Rust `llm.rs`) | TS |
| 5 | **Assemble** | собирает claims, считает confidence, сливает с прошлой моделью, сохраняет | нет | TS + Rust store |
| 6 | **Render** | markdown и диаграммы из модели (`Renderer`) | нет | TS, запись через Rust |
| 7 | **Index** | `Indexer` обновляет FTS | нет | Rust |

Ревью — не стадия пайплайна, а отдельный процесс над результатом Assemble (см. `04-review.md`). Render и Index публикуют подтверждённое; непроверенное отдаётся с явным статусом.

## RunContext

Аналог `RunContext` из worklog-tracker: настройки, опции запуска, накопленные факты, предупреждения, логгер, доступ к LLM. Дополнительно: идентификатор запуска, целевой коммит, версии экстракторов и промптов, прошлая модель сервиса. Состояние (`RunState`) сериализуется в чекпойнт после каждой стадии.

## Политика ошибок

Одна общая политика на все источники и экстракторы (как `sourceStep` в `steps.ts`):

- `enabled(ctx)` — включён ли шаг; иначе в лог пишется причина пропуска;
- `required = true` — сбой прерывает запуск; иначе сбой даёт предупреждение и запуск продолжается;
- ошибки — коды `HubError(code, params)`, текст формирует UI.

## Discover, Trace, Assemble (M3)

- **Discover** (`src/lib/stages/discover.ts`): одна фича на точку входа. Группа и действие — из тега и `operationId` OpenAPI, иначе из пути (`POST /api/v1/refunds` → `refunds/create`, `GET /refunds/{id}` → `refunds/get`, `POST /refunds/{id}/approve` → `refunds/approve`), иначе из класса и метода. Если триггер уже был в прошлой модели, id фичи берётся оттуда — после ревью id не меняются. Внутренние события (`publishEvent`) не становятся отдельными фичами: они прослеживаются внутри публикующего потока.
- **Trace** (`src/lib/stages/trace.ts`): обход от метода-обработчика по вызовам между бинами до стоков. Интерфейс с одной реализацией — статический вызов; с несколькими — все реализации с `INFERRED/LOW` и обрыв `MULTIPLE_IMPLEMENTATIONS`. Событие → обработчик — ребро `INFERRED/MEDIUM`. Плейсхолдеры `${...}` подставляются из конфигурации; не найденные — обрыв и `LOW`. Таблица, которой нет в миграциях, получает не выше `MEDIUM`.
- **Assemble** (`src/lib/stages/assemble.ts`): claims на каждый триггер (`EXISTS` — STATIC; `BELONGS_TO_FEATURE` — INFERRED, границы фич эвристичны), на каждое ребро, на бизнес-названия. Владелец — по CODEOWNERS. Затем слияние с прошлой моделью (`src/lib/model/merge.ts`): отклонённое остаётся отклонённым, подтверждённое при изменении кода становится `STALE`, изменение подтверждённого — дифф на ревью, правка человека не перезаписывается (конфликт), исчезнувшая фича с проверенными claims остаётся со статусом `STALE`. Названия в модели выводятся из claims `DESCRIBES`.

Golden-тест стадий 2–5 работает на реальном выводе Rust-сканера по фикстуре (`refunds-service.scan.json`); модель, которую он строит (`refunds-service.model.json`), Rust-тест хранилища проверяет на сохранение без потерь.

## Describe (M4)

`src/lib/stages/describe.ts`: фичи пачками по 8 уходят в LLM (`llm_chat` в Rust, OpenAI-совместимый API). В запросе только имена триггеров, шагов, компонентов и стоков — без кода; текст проходит редакцию секретов (`src/lib/redact.ts`). Промпт — на языке анализа (`src/lib/prompt.ts`, версия пишется в метаданные запуска). Ответ — JSON с названиями и описаниями; всё попадает в claims `DESCRIBES` (`INFERRED/MEDIUM`) и идёт на ревью. Названия, уже подтверждённые или исправленные на ревью, повторно не запрашиваются.

## Ход анализа и журнал

Экран «Анализ» показывает стадии со статусом (готово / идёт / пропущено / ошибка), строку «Сейчас» с прогрессом текущей стадии и журнал:
- **Прогресс** не сохраняется, только показывается (`RunContext.progress`): какой файл разбирает экстрактор (Rust шлёт события `scan-progress` не чаще раза в 50 мс), какую фичу трассирует Trace, какой запрос к LLM идёт или сколько секунд пауза до следующего.
- **Журнал** — записи с кодами (`RunContext.log`), сохраняются в `.state/hub.db` и открываются для прошлых запусков. Уровень `detail` — отдельные элементы (найденная фича и почему так сгруппирована, поток фичи со стоками и обрывами, каждый запрос к LLM с длительностью); переключатель «Подробно» их скрывает. Остальное — итоги: что нашёл каждый экстрактор и источник и за сколько, итог слияния с ревью (сколько на проверку, сколько проверенного сохранено, сколько устарело), предупреждения.

Ответ LLM приходит потоком (`llm_chat_stream`, SSE OpenAI-совместимого API; шлюз без потока тоже работает): в строке «Сейчас» видно, сколько секунд идёт запрос и что модель уже написала; по готовности в журнал пишется каждое полученное название. Состояние запуска живёт вне экрана (`components/run/runStore.ts`): анализ продолжается, а лог и прогресс сохраняются при переходе на другие вкладки; в навигации у «Анализ» крутится индикатор, пока идёт запуск.

## Прогоны: статический и ИИ

Экран «Анализ» — список прогонов репозитория слева и выбранный прогон справа: стадии, результат (из сохранённого чекпойнта: фичи, компоненты, таблицы, свойства, ошибки разбора, названия от ИИ), проблемы разбора и журнал. Любой прошлый прогон открывается так же; упавший или прерванный — продолжается с первой незавершённой стадии.

Анализ идёт в два шага:
- **Статический** (`mode = static`): все стадии, Describe пропускается (`staticRun`). Бизнес-названия, полученные раньше, сохраняются слиянием моделей.
- **ИИ-описание** (`mode = llm`, `describeRun` в `lib/pipeline.ts`): берёт результат завершённого статического прогона из его чекпойнта (`scan`, `candidates`, `traced`, каталог), помечает Scan/Discover/Trace выполненными и выполняет Describe → Assemble → Render → Index. Код заново не разбирается, коммит — тот же, `basedOn` указывает на исходный прогон. Если код изменился с тех пор, экран предупреждает.
- Переключатель «Затем ИИ-описание» запускает оба прогона подряд. Старые прогоны без `mode` показываются как `full` или `static` по флагу `describe`.

Обмен с LLM остаётся в журнале: что ушло (`llmRequestText`, подробно), ответ (`llmAnswerText`, подробно), неполный ответ — какие фичи остались без названия и какие id лишние (`llmIncomplete`, предупреждение с текстом ответа), ответ, который не удалось разобрать (`llmUnclearAnswer`, предупреждение с текстом). Тексты длиннее 20 000 символов обрезаются; на экране они свёрнуты, предупреждения раскрыты.

## Ограничение запросов к LLM

Настройки → LLM: «Запросов в минуту» (по умолчанию 6) и «Максимум запросов за анализ» (по умолчанию 20; запрос — до 8 фич). Describe делает паузы между запросами (`RateLimiter`), не отправляет больше лимита за запуск (остальные фичи остаются с техническими именами, в журнале — `llmBudgetExceeded`), на HTTP 429 от шлюза повторяет запрос через 15 и 30 секунд. Названия, уже подтверждённые на ревью, повторно не запрашиваются — повторные анализы тратят запросы только на новое.

## Деградация без LLM

Если LLM недоступна или вернула мусор, стадии 1–3 и 5–7 всё равно дают модель со статическими фактами и техническими названиями. Стадия Describe пишет предупреждение `businessNamesMissing` с числом фич без названий (как откат `AiAllocator` на `HeuristicAllocator`); если LLM не настроена или недоступна, остальные пачки не запрашиваются.

## Что даёт экстрактор Kotlin + Spring Boot

**Входы (триггеры):**
- `@RestController` / `@Controller` + `@GetMapping`, `@PostMapping`, `@RequestMapping` и др. (с учётом префиксов путей);
- `@KafkaListener`, `@RabbitListener`, `@JmsListener`, другие слушатели сообщений;
- `@Scheduled`, `@EventListener`, `ApplicationRunner`/`CommandLineRunner`;
- `@Async` (на методе или на классе): если метод вызывается из кода проекта — это асинхронный шаг вызывающего потока (в потоке помечен «асинхронно», в L3 — асинхронная стрелка); если никто в проекте его не вызывает — отдельная фича (группа «Асинхронные задачи»). Так же, как внутренние события, — чтобы одни и те же утверждения не проверялись дважды.

**Внутренние узлы:**
- бины `@Service`, `@Component`, `@Repository`, `@Configuration`, внедрение через конструктор;
- граф вызовов между бинами.

**Стоки:**
- JPA: `@Entity`, `@Table`, `JpaRepository`/`CrudRepository`; Spring Data JDBC; `JdbcTemplate`/`NamedParameterJdbcTemplate`; jOOQ/Exposed (по мере необходимости);
- сообщения: `KafkaTemplate`, `RabbitTemplate`, `StreamBridge`;
- исходящий HTTP: Feign-клиенты, `WebClient`, `RestTemplate`, `RestClient`;
- миграции Flyway/Liquibase для схемы таблиц.

**Контекстные источники (`ContextSource`):** OpenAPI-спецификация, `application.yml` (топики, URL клиентов), README/ADR.

**Шаблоны и обобщённые репозитории.** Вызовы `R2dbcEntityTemplate`, `JdbcAggregateTemplate`, `EntityManager`, `MongoTemplate`, `ElasticsearchOperations`, `CassandraTemplate` (и их reactive/Operations-варианты) — обращения к хранилищу: `insert/update/delete/save/persist/merge/remove…` — запись, `select/find/count/exists/query…` — чтение; `createQuery`/`createNativeQuery` — по тексту запроса. Сущность берётся из аргумента: `Foo::class.java`, `Foo(…)`, параметр типа `Foo` или `T`, поле `KClass<T>`/`Class<T>` (`kClazz.java`). Методы обобщённого базового класса (`abstract class AbstractRepository<T, ID>(template, kClazz)`) приписываются каждому бину-наследнику, а `T` подставляется из его объявления (`RefundDao : AbstractRepository<RefundEntity, UUID>`), так что `dao.insert(x)` из сервиса доходит до таблицы `RefundEntity` (уверенность MEDIUM: метод может быть переопределён). Не найденная сущность — `UNRESOLVED_CALL`.

**Слабые места статики (идут в INFERRED):** вызовы через интерфейсы с несколькими реализациями, события через `ApplicationEventPublisher`, рефлексия, динамические SQL, межсервисные связи по общему топику. Восстановление после ошибок: объявления, которые грамматика всё же распознала внутри ERROR-узла (классы, функции, свойства), не теряются. Строки с несколькими долларами (`$$"""…"""`, Kotlin 2.1+) грамматика не знает: перед разбором лишние `$` заменяются пробелами той же длины. Так же убирается висячая запятая перед `]` (`map[
 key,
]` — допустимо в Kotlin, неизвестно грамматике); строки и комментарии при этом не трогаются. Ещё три особенности грамматики обходятся так же, без сдвига позиций: кавычки в конце текста raw-строки (`"""…"""""` — Kotlin закрывает строку последними тремя) становятся пробелами; в строке аннотации после свойства класса пробел в `) &&`, `) >`, `) .` заменяется на `_` (иначе грамматика теряет остаток класса); идентификатор `dynamic` (в грамматике — тип Kotlin/JS) становится `dynami_`. Имена и литералы модель читает из исходного текста, поэтому замены в неё не попадают. Если грамматика отбросила всё тело `{ … }` класса, тело разбирается отдельно, и в отчёт добавляется место, где падает уже оно, — обычно это и есть причина. Для первой ошибки файла `diagnose.rs` разбирает файл повторно, по очереди обезвреживая комментарии, текст строк, не-ASCII символы (невидимые и пробельные — пробелом) и табуляции; если ошибка исчезает, ищется конкретный литерал или строка кода, и в отчёт идёт только его форма: где он относительно ошибки, длина, классы символов, ASCII-пунктуация и коды особых символов (`U+00A0`). Не больше 300 повторных разборов на файл. В отчёте о проблемах разбора: окно ±3 строки с пометкой `// <-- parse error`, обезличенный неразобранный текст и отметка «первая ошибка в файле / возможно, следствие». Известные особенности грамматики: однострочный `companion object { val … }` не разбирается (→ `PARSE_ERROR`); аннотации после star-импорта грамматика отрывает от класса — `syntax.rs` возвращает их на место.

**Как это устроено (M2):** `src-tauri/src/extract/kotlin_spring/` — `syntax.rs` превращает дерево tree-sitter в маленькую модель (классы, аннотации, параметры конструктора, вызовы с цепочками), `spring.rs` переводит её в факты:
- бины — классы со стереотипами, интерфейсы Spring Data, Feign-клиенты, классы со слушателями, типы из `@Bean`-методов;
- типы полей резолвятся по импортам, пакету и star-импортам; константы (`const val`, `Owner.NAME`) и `@Value("${...}")` подставляются в имена топиков и URL;
- репозиторий Spring Data даёт READ/WRITE своей таблицы на каждый объявленный или вызванный метод (`save*`, `delete*`… и `@Modifying` — запись);
- литеральный SQL `JdbcTemplate` разбирается на таблицы; нелитеральный — обрыв `DYNAMIC_SQL`;
- строки, которые грамматика не разобрала, становятся фактом `PARSE_ERROR` (файл виден ревьюеру, а не теряется молча). Для каждой ошибки Rust сохраняет место в дереве разбора (`class_declaration › class_body › ERROR`) и обезличенный фрагмент (`anon.rs`: ключевые слова и известные имена Kotlin/Spring остаются, имена проекта → `A1`/`x1`, слова в строках → `…` (кавычки, `$`, `{}`, `[]` и `\` остаются — это форма строки, а не её содержание), числа → `0`, комментарии убраны). Экран «Анализ» группирует ошибки по конструкции; отчёт для чата содержит только конструкции — без путей, номеров строк и коммита, его можно отправлять за пределы команды.

Контекстные источники (`src-tauri/src/context/`): `spring-config` (application*.yml/properties, секреты маскируются), `openapi`, `migrations` (схема из Flyway/Liquibase: таблицы, колонки, ключи с учётом alter/rename/drop), `codeowners`. Экстрактор Kotlin/Spring дополнительно отдаёт JPA-сущности и места чтения конфигурации; стадия Assemble собирает из них `database` и `config` (`src/lib/model/database.ts`, `config.ts`).

**Разбор кода** — tree-sitter (грамматика Kotlin) в Rust: быстро, без JVM, но без резолва типов. Типы полей резолвятся эвристически (импорты, пакет, конструктор). Точный разбор (PSI/компилятор Kotlin) возможен позже как отдельный внешний помощник за тем же трейтом `Extractor`; на старте не нужен.

## Детерминизм и проверка качества

Результат стадий 1–3 тестируется golden-тестами на небольшом fixture-проекте (`src-tauri/tests/fixtures/`): Rust-тест для Scan, vitest для Discover/Trace. Для реального сервиса качество экстракции сверяется с эталоном (например, список маршрутов из `/actuator/mappings` или OpenAPI), см. критерии в `09-roadmap.md`.

## Контекст для LLM

В LLM уходит минимальный срез: сигнатуры, аннотации, фрагменты с evidence, а не весь файл. Секреты и значения конфигурации с признаками секретов редактируются заранее. Размер среза ограничивается контекстом корпоративной модели.
