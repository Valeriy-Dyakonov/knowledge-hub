# 03. Пайплайн анализа

Образец — `pipeline.ts` из worklog-tracker: `AnalysisPipeline` только оркестрирует стадии, общий `RunContext` передаётся каждой.

## Стадии

| # | Стадия | Что делает | LLM |
|---|---|---|---|
| 1 | **Scan** | `Extractor` и `ContextSource` собирают точки входа, компоненты, вызовы, обращения к хранилищам и внешним системам | нет |
| 2 | **Discover** | группирует точки входа в кандидатов-фичи (по пакетам, путям, аннотациям, тегам OpenAPI) | опционально: именование |
| 3 | **Trace** | для каждой фичи строит граф от триггера до стоков; помечает обрывы (DI, рефлексия, события) | нет |
| 4 | **Describe** | бизнес-названия, краткие описания, пояснения шагов | да |
| 5 | **Assemble** | собирает claims, считает confidence, формирует очередь ревью | нет |
| 6 | **Render** | markdown и диаграммы из модели (`Renderer`) | нет |
| 7 | **Index** | `Indexer` обновляет FTS/вектор | нет |

Ревью — не стадия пайплайна, а отдельный процесс над результатом Assemble (см. `04-review.md`). Render и Index публикуют подтверждённое; непроверенное отдаётся с явным статусом.

## RunContext

Аналог `RunContext` из worklog-tracker: настройки, опции запуска, накопленные факты, предупреждения, логгер, ссылка на LLM-клиент. Дополнительно: идентификатор запуска, целевой коммит, версии экстракторов и промптов.

## Политика ошибок

Одна общая политика на все источники и экстракторы (как `sourceStep` в `steps.ts`):

- `enabled(ctx)` — включён ли шаг; иначе в лог пишется причина пропуска;
- `required = true` — сбой прерывает запуск; иначе сбой даёт предупреждение и запуск продолжается;
- ошибки — коды `HubError(code, params)`, текст формирует UI.

## Деградация без LLM

Если LLM недоступна или вернула мусор, стадии 1–3 и 5–7 всё равно дают модель со статическими фактами и техническими названиями. Стадия Describe помечает бизнес-названия как отсутствующие (как откат `AiAllocator` на `HeuristicAllocator`).

## Что даёт экстрактор Kotlin + Spring Boot

**Входы (триггеры):**
- `@RestController` / `@Controller` + `@GetMapping`, `@PostMapping`, `@RequestMapping` и др. (с учётом префиксов путей);
- `@KafkaListener`, `@RabbitListener`, `@JmsListener`, другие слушатели сообщений;
- `@Scheduled`, `@EventListener`, `ApplicationRunner`/`CommandLineRunner`.

**Внутренние узлы:**
- бины `@Service`, `@Component`, `@Repository`, `@Configuration`, внедрение через конструктор;
- граф вызовов между бинами.

**Стоки:**
- JPA: `@Entity`, `@Table`, `JpaRepository`/`CrudRepository`; Spring Data JDBC; `JdbcTemplate`/`NamedParameterJdbcTemplate`; jOOQ/Exposed (по мере необходимости);
- сообщения: `KafkaTemplate`, `RabbitTemplate`, `StreamBridge`;
- исходящий HTTP: Feign-клиенты, `WebClient`, `RestTemplate`, `RestClient`;
- миграции Flyway/Liquibase для схемы таблиц.

**Контекстные источники (`ContextSource`):** OpenAPI-спецификация, `application.yml` (топики, URL клиентов), README/ADR.

**Слабые места статики (идут в INFERRED):** вызовы через интерфейсы с несколькими реализациями, события через `ApplicationEventPublisher`, рефлексия, динамические SQL, межсервисные связи по общему топику.

**Реализации разбора кода** — за одним интерфейсом, выбираются на прототипе:
- лёгкая: tree-sitter (Kotlin), быстро, но без резолва типов;
- точная: PSI/символьный разбор через Kotlin-компилятор, резолвит вызовы через интерфейсы и DI, тяжелее.

## Детерминизм и проверка качества

Результат стадий 1–3 тестируется golden-тестами на небольшом fixture-проекте. Для реального сервиса качество экстракции сверяется с эталоном (например, список маршрутов из `/actuator/mappings` или OpenAPI), см. критерии в `09-roadmap.md`.

## Контекст для LLM

В LLM уходит минимальный срез: сигнатуры, аннотации, фрагменты с evidence, а не весь файл. Секреты и значения конфигурации с признаками секретов редактируются заранее. Размер среза ограничивается контекстом корпоративной модели.
