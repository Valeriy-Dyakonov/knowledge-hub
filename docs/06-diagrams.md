# 06. Диаграммы

Диаграммы **генерируются из модели** рендерером, а не рисуются LLM. Так они единообразны, согласованы с текстом и ревьюятся через claims.

## Уровни

| Уровень | Что показывает | Аудитория |
|---|---|---|
| L1. Контекст | сервис, пользователи/системы вокруг него, внешние зависимости | все, включая нетехнических |
| L2. Компоненты | основные блоки сервиса, хранилища, очереди, внешние API | разработчики, аналитики |
| L3. Поток фичи | sequence: триггер -> шаги -> сток | разработчики и ревьюеры |

## Правила читаемости

- Не более 10–12 узлов на диаграмму; больше — делим по подфичам или группируем.
- Подписи — `businessName`; технические названия показываются в подсказке/вторым уровнем.
- Единые формы и цвета по виду узла: триггер, компонент, БД, очередь, внешний сервис.
- Направление слева направо; триггеры слева, стоки справа.
- Каждый узел и ребро связаны с claim (для перехода к evidence и ревью).

## Формат

Начинаем с Mermaid (текстовый, диффится, рендерится во многих средах). Рендерер — интерфейс, так что D2/C4/другие форматы добавляются реализацией. В приложении диаграммы рисуются библиотекой `mermaid` из того же текста; клик по узлу открывает его claims и evidence.

## Реализация (M4)

`src/lib/render/mermaid.ts` — три функции, одни и те же для файлов и для приложения:
- **L1** `contextDiagram`: сервис в центре; слева клиенты API (одним узлом с числом эндпоинтов), топики, которые он слушает, расписание, события; справа база данных (одним узлом с числом таблиц), публикуемые топики, внешние API. Больше 4 топиков или внешних API — один групповой узел.
- **L2** `componentsDiagram`: компоненты и стоки, с которыми они работают. Больше 12 узлов — сначала стоки группируются по виду, затем, если не хватило, компоненты по виду (Контроллеры (3), Сервисы (5)…).
- **L3** `flowDiagram`: sequence-диаграмма фичи в порядке шагов. Больше 12 участников — компоненты одного вида делят одну линию. Выведенные связи (`INFERRED`) — пунктирные стрелки с пометкой.

Формы и цвета: триггер — овал, компонент — прямоугольник, БД — цилиндр, очередь/топик — параллелограмм, внешний сервис — шестиугольник. Связи с отклонёнными claims в представления не попадают. Перед каждым ребром — комментарий `%% claim <id>`. Подписи — бизнес-названия, иначе технические.

В приложении — вкладка «Схемы» (L1/L2) и диаграмма потока на карточке фичи. Тесты проверяют синтаксис каждой диаграммы через `mermaid.parse` и ограничение на число узлов.

## Ревью диаграмм

Ревьюер видит превью и список claims, из которых оно собрано. Правка идёт в модели; диаграмма перестраивается. Ручной правки изображений нет.
